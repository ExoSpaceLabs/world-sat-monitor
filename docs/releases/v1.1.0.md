# WorldSat Monitor v1.1.0

## Scope

v1.1.0 improves resilience and observability of the existing CelesTrak + SGP4 satellite and constellation platform. The rendering, propagation, management, and Docker Compose architecture from v1.0.0 are retained.

### Provider request resilience
- Configurable bounded CelesTrak HTTP retries and request timeout.
- Exponential, persistent per-satellite/provider backoff; provider-defined group fetch backoff.
- Process-local catalog cache with stale-cache fallback during transient outages.
- Local catalog search by name and stored identifiers when the upstream catalog cannot be reached.
- Retention and continued use of locally stored orbital elements/propagation products during source outages.

### Source quality and observability
- `GET /api/v1/satellites/{satellite_id}/orbital-status`: provider health, candidate chain, last success/failure, next retry, element epoch/fetch time, freshness, and propagated-state provenance.
- `GET /api/v1/groups/{group_id}/orbital-status`: bounded aggregate group source/coverage/health/age summary and highest-attention members.
- Satellite and group Details show corresponding operational quality metadata.

### Provider selection
- Ordered `provider_priority` per satellite with per-source health/backoff and failover.
- The older `provider_preference` remains as a compatibility alias, but runtime selection uses `provider_priority`.
- `GET /api/v1/providers` advertises enabled providers and capabilities.
- In this release, the supported provider registry includes CelesTrak and the deterministic mock provider. **Space-Track is not yet implemented.**

## Upgrade from v1.0.0

1. Back up PostgreSQL and persistent application settings volumes.
2. Deploy using `WORLDSAT_IMAGE_TAG=1.1.0 docker compose -f compose.images.yaml pull` and `WORLDSAT_IMAGE_TAG=1.1.0 docker compose -f compose.images.yaml up -d`.
3. Confirm `/api/v1/health` and the provider/propagator container health checks.
4. Confirm `/api/v1/providers` responds and review the source age/health shown in satellite/group Details.
5. Inspect provider-worker logs and verify a monitored satellite successfully acquires and propagates an element set.

Schema migration adds provider selection and resilient state metadata. Source updates must be treated as untrusted inputs; a stale locally retained element set is a **degraded fallback**, not an orbital-position accuracy guarantee.

## Operational considerations

- In-memory catalog cache is **per provider process**, not shared across replicas. Persistent per-satellite backoff is stored in PostgreSQL.
- Freshness categories describe age relative to provider polling policy, not orbit-determination accuracy.
- Space-Track, multi-source comparison, and reference-based prediction-quality metrics remain scoped to [issue #19](https://github.com/ExoSpaceLabs/world-sat-monitor/issues/19).
- Further constellation-scale optimizations are tracked in [issue #18](https://github.com/ExoSpaceLabs/world-sat-monitor/issues/18).

## Release verification

The release must pass the repository CI suite on the release PR and the final `main` commit before images are published:
- frontend lint, build, tests, artifact validation, constellation rendering benchmark;
- backend/SGP4/provider contract and failover tests;
- PostgreSQL legacy migration and provider-group import integration;
- 100, 1,000, 5,000 satellite/group performance benchmark;
- full Docker Compose provider → propagator → API integration.

The `main` publish workflow creates `v1.1.0` only after successful validated images are published. Do not manually move or pre-create the release tag.
